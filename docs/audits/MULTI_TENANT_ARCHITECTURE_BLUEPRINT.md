# Flash — Multi-Tenant Architecture Blueprint (v2, corrected)

**Scope:** Analysis and a written roadmap only. No migration was written, no real table was touched, no existing Flash file was modified producing this document. Every claim below is cited to a real file:line in this repo, cross-referenced against `docs/audits/ADMIN_PANEL_AUDIT_AND_VISION.md` (all rounds) and `backend/src/config/adminCoverage.js` rather than re-derived, per this task's own instruction. Where Saleor is referenced, it's the real, cited findings from `SALEOR_ARCHITECTURE_STUDY.md`, not general knowledge. Nothing here should be implemented without the founder's explicit approval of a specific phase, in a future, separate session.

**Correction note:** this document originally assumed store-scoped admin roles ("Store Manager," etc.) would be expressed as `admins.role` values, authenticated through the existing internal-admin JWT/session system. The founder has since explicitly corrected this: the Store Admin Portal is a genuinely separate system for partner stores, with its own `store_users` table and its own auth domain, entirely distinct from `admins`. Every passage below that referenced extending the existing admin auth/role system for store scoping has been corrected to reference the new, separate system instead — see `FLASH_STORE_ADMIN_DESIGN.md` §3 for the full design. Two other things changed since this document was first written and are reflected below: `orders.store_id` is now genuinely `UUID` (migration v27, no longer the `VARCHAR` inconsistency §1.1 originally flagged), and the store-facing order-acceptance workflow (§1.3 originally speculative) is now real and live (`pending_store_acceptance`/`preparing` states, a real `order_status_enum` Postgres type, a 15-minute timeout cron).

## 1. What would actually be required, precisely

### 1.1 A real inconsistency — now partially resolved, tracked here for accuracy

**Update since this document was first written: `orders.store_id` is now genuinely `UUID`** (migration v28's predecessor, v27 — `ALTER TABLE orders ALTER COLUMN store_id TYPE UUID USING store_id::uuid`, verified live against production), and `orderController.createOrder` was corrected in the same change to stop trusting any client-supplied value for it (it now explicitly inserts `store_id: null` — a real store lookup, per §1.4 below, is still the pending piece of work, not yet built). The type-inconsistency risk this section originally flagged for `orders.store_id` specifically is closed.

**Still open, unchanged from the original finding:** `store_boosts.store_id`, `store_promotions.store_id`, `brand_size_mappings.store_id` remain `VARCHAR(100)` free-text tags, never a foreign key (`migrate.js:185, 455, 497, 505` — original line numbers, file has grown since). `store_boosts`/`store_promotions` are the only tables that actually populate this column today, always the literal string `"flash_closet"` (per `adminCoverage.js`'s own comment on `store_boosts`). `order_cancellation_store_shares.store_id` is genuinely `UUID`, nullable, with **no** FK constraint (`migrate.js:1279`) — the real placeholder for a future `stores.id`, explicitly documented in that migration's own comment as "the explicit multi-store extension point... store_id is always NULL until multi-store orders exist."

**Why this still matters for the blueprint:** the day a real `stores` table is introduced, `store_boosts`/`store_promotions`/`brand_size_mappings` need the same one-time conversion `orders.store_id` already got (map the single existing value `"flash_closet"` to whatever UUID the first seeded `stores` row gets, then convert the column type to `UUID REFERENCES stores(id)`), and `order_cancellation_store_shares.store_id` needs the FK constraint added, since its type was already chosen correctly. This is real, cheap, one-time work, now a smaller remaining surface than originally scoped — flagged here so it's planned for, not discovered mid-migration.

### 1.2 Every table that would need real store-scoping — checked against the full, real 49-table inventory in `adminCoverage.js`, not assumed

| Table | Needs `store_id`? | Why / current state |
|---|---|---|
| `orders` | **Yes — already has the column, wrong type, always null** | Core transactional table. Needs the type fix in §1.1, and `orderController.createOrder` needs to actually populate it from a real store lookup instead of never setting it (§1.4). |
| `order_items`, `order_cancellations`, `order_cancellation_store_shares`, `return_requests`, `return_request_items`, `payments`, `payment_refunds` | **No — inherit scope via `order_id`** | All FK to `orders` already; a store filter on any of these is a join through `orders.store_id`, not a new column. Denormalizing a copy of `store_id` onto each is a real, valid *performance* optimization once query volume justifies it (§4 below), not a correctness requirement. |
| `flash_inventory` | **Yes — the real, structural gap, not a column addition** | Confirmed via `SALEOR_ARCHITECTURE_STUDY.md` §1.4: Flash's inventory is one `stock_by_size` JSONB column per product — a single, store-wide count. Saleor's real answer to multi-location stock is a genuine `Stock` join table (`warehouse_id` × `product_variant_id`, independent quantity per pair) — the same shape Flash would need the day two physical stores each hold their own independent stock of the same item. This is **not** an additive `store_id` column on the existing table; it's a new join table (`store_stock`: `store_id`, `product_id`, `size`, `quantity`), and every stock read/write path (`Order.create()`'s stock-decrement logic, `Inventory.js`'s CRUD) would need to target the right store's row instead of the product's own column. Correctly the single most involved item in this whole blueprint — flagged precisely so it isn't underestimated as "just add a column" the way most of the rest of this table is. |
| `store_boosts`, `store_promotions`, `brand_size_mappings` | **Yes — already have the free-text column, needs the type fix** | Same §1.1 fix. |
| `driver_wallets`, `driver_wallet_ledger`, `driver_payout_requests`, `payout_transactions` | **No — driver-scoped, not store-scoped, by design** | A driver's wallet is a single, per-driver aggregate that can be credited by orders from *any* store, since Flash's driver pool is shared city-wide (confirmed: `autoMatchService.js`'s nearest-driver query, `autoMatchService.js:36-56`, has zero store filtering — it matches purely on proximity to `orders.pickup_lat/pickup_lng` across the whole online driver pool). Adding `store_id` to the wallet tables would incorrectly imply a driver has a separate wallet per store, which isn't how Flash's delivery model works and shouldn't be forced to work that way. This is a real, deliberate **non-requirement** — named explicitly so it isn't defaulted into "every table gets a store_id" without checking. |
| `driver_commission_debts` | **No — this is Flash's own platform revenue, not a store's** | The R20 cash-order commission is Flash's cut for operating the delivery/logistics, charged regardless of which store the order came from — it's platform-level revenue, not store revenue. Traceable to a store via `orders` if ever needed for reporting, but doesn't belong to a store the way `order_cancellation_store_shares.amount` does. |
| `driver_subscriptions`, `premium_subscriptions`, `premium_subscription_payments`, `driver_ratings`, `app_ratings` | **No** | All either driver/user-scoped (subscriptions, app rating) or tied to a specific delivery via `order_id` (driver rating) — none represent a store's own data. |
| `admins`, `admin_actions` | **No — resolved, not a decision point anymore** | Corrected: store-scoped roles ("Store Manager," etc.) are **not** `admins.role` values at all. They live in a new, separate `store_users` table (`store_id` is a required, non-nullable FK there by construction), with its own auth domain entirely — see `FLASH_STORE_ADMIN_DESIGN.md` §3. `admins`/`admin_actions` stay exactly as they are today: flat, platform-wide, Flash-team-only, zero store concept, zero changes needed. |
| `flagged_accounts`, `sos_alerts`, `driver_documents`, `messages`, `feed_posts`, `feed_comments`, everything else in `adminCoverage.js`'s `covered`/`intentionallyExcluded` lists | **No** | User/driver/content-scoped, not store-scoped — a flagged account, an SOS alert, a chat message, or a feed post doesn't belong to a store any more than the user or driver themselves does. |

**Net count: 2 tables need a real, new/fixed `store_id` (`orders`, and the 3 free-text-tag tables sharing the same fix), plus one genuinely new table (`store_stock` or equivalent) for inventory.** Everything else either inherits scope via an existing FK or has a real, considered reason not to need one at all — a much smaller surface than "add `store_id` everywhere" would suggest, and precisely why checking the real 49-table list mattered instead of assuming.

### 1.3 Services and controllers that would need to become store-aware

- **`orderController.createOrder`** (`orderController.js:107-140`) — the actual bottleneck, confirmed by direct reading, not assumed: pickup is hardcoded to the single `FLASH_STORE_LOCATION` constant *at the controller layer*, with an explicit, deliberate security comment explaining why client-supplied pickup coordinates are never trusted (`orderController.js:107-113`). This is genuinely good news structurally: `Order.create()` itself (`Order.js:65-71`) already accepts arbitrary `pickup_lat`/`pickup_lng` and computes delivery fee from real distance — it is **not** hardcoded at the model layer. Multi-store support here is "teach the controller to look up a real store's registered, server-trusted address by `store_id` instead of using the one constant" — a contained, well-isolated change, not a rewrite.
- **`autoMatchService.js`** (`autoMatchService.js:24-60`) — currently matches the nearest *online* driver to an order's pickup point from the entire city-wide pool, with zero store filtering. This is very likely still the *correct* behavior even with multiple stores (Flash's real value proposition is a shared, efficient driver pool, not siloed per-store couriers) — but it's a real design decision to make explicitly, not silently inherit: does a future multi-store Flash want (a) the current behavior unchanged, any online driver can serve any store's order, or (b) drivers who can opt into/be assigned to specific stores? Recommendation: **keep (a)** unless a real operational reason emerges to change it — it requires zero code changes and matches how Flash's delivery model already works today.
- **`geoBoundary.js`** — `FLASH_STORE_LOCATION` (a single hardcoded lat/lng) and `NMB_BOUNDS` (a single hardcoded bounding box covering one metro) are both real, current bottlenecks: the moment a second store exists in a *different* city, the single bounding box is simply wrong for it. This needs to become a per-store service-area definition, looked up by `store_id`, not a global constant — a real, necessary change, not optional.
- **Driver app navigation — confirmed already correctly store-aware, zero changes needed.** `flash-driver-app/app/driver/dashboard.js:498` reads `activeOrder.pickup_lat`/`activeOrder.pickup_lng` (the real, per-order stored value) for the "Navigate to Store" button — **not** a separate hardcoded constant. Since this already reads the order's own value, the driver app requires no changes at all once `orderController.js` starts populating that field from a real store lookup instead of the one constant. A genuinely well-positioned piece of the existing system, worth naming as such rather than assuming everything needs rework.
- **`Inventory.js` / `inventoryController.js` / `flash_inventory`'s stock read-write paths** — need to become store-scoped the moment the `store_stock` join table (§1.2) exists; every stock check/decrement in `Order.create()`'s item-validation loop (`Order.js:142-212`) currently checks `flash_inventory.stock_by_size` directly and would need to check the right store's stock row instead.
- **`Admin.getFinancials()` / `Admin.getDailyTrends()`** (`Admin.js`) — every aggregate query in these two functions would need an optional `store_id` filter/group-by added once multiple stores exist, so a founder (or eventually a Store Manager, per Phase 3) can see one store's numbers, not just the platform-wide total. Straightforward, additive `WHERE`/`GROUP BY` changes to existing queries — no new tables needed for this part.

### 1.4 API tenant isolation — the real risk, same rigor as an ownership/IDOR bug

This is the single highest-stakes technical point in this document, stated as plainly as this engagement's own security audits have stated IDOR risk: **a missing tenant check is structurally the exact same class of bug as a missing ownership check — just at a coarser grain.** Every endpoint this engagement has already hardened against "can user B read/modify user A's data" (e.g., `Payment.getSavedCardById(cardId, userId)`'s `WHERE id=$1 AND user_id=$2` scoping, confirmed and reused correctly as recently as tonight's subscription-cancellation work) would need the **identical discipline applied one level up**: "can an admin/manager scoped to Store A read/modify Store B's orders, inventory, or financials."

Concretely, once multi-store exists, every admin-facing query that currently has no store filter (which is all of them today, since there's only one store) becomes a real IDOR-shaped risk the moment a second store's admin account exists — the exact same bug class, at the store grain instead of the user grain. The fix is the same shape already proven throughout this codebase: **every store-scoped query must include `AND store_id = $storeIdFromTheAuthenticatedCaller` in its `WHERE` clause, never a client-suppliable parameter** — matching `orderController.js`'s own existing reasoning almost verbatim ("trusting a client-sent pickup coordinate... would just be an unnecessary way for a bad client to bypass this check," `orderController.js:110-112`). The founder should expect and demand the exact same "verify live, attempt cross-tenant access with a real second account, confirm it's cleanly rejected" standard already applied to every ownership check this engagement has shipped, the day this is actually built — not assumed safe because a query "should" filter correctly.

### 1.5 Authentication/authorization changes

Confirmed by direct read of `helpers.js:15-31` (`generateToken`): the real, current JWT payload is exactly `{ id, role, jti, status? }` — **no `store_id` claim exists anywhere today**, for any of the three token types (user, driver, admin). This is expected for a single-store system and is not itself a problem to fix now.

For a real multi-store future, the precise question isn't "does every JWT need a `store_id` claim" — it's role-specific:
- **Store Admin Portal users (`store_users`, corrected from "Admins" above)**: yes — a `storeId` claim is the entire point of that token type. This is a **new, separate JWT domain** (`STORE_JWT_SECRET`, per `FLASH_STORE_ADMIN_DESIGN.md` §3.1), not an addition to the existing admin JWT.
- **Internal Flash admins (`admins`)**: **no** — stays exactly as it is, no `store_id` claim, since the internal panel is platform-wide by design and this correction explicitly keeps it that way.
- **Drivers**: almost certainly **no**, per §1.3's recommendation to keep the shared, city-wide driver pool — a driver isn't scoped to a store, so their JWT doesn't need to be either.
- **Users/customers**: **no** — a customer isn't tenant-scoped at all; they simply place an order that happens to specify (or default to) a store at checkout time, the same way a Saleor customer isn't "a member of" one Channel.

Flash's existing `requireRole()` (`middleware/auth.js:106-111`) already proves the *shape* of role-gated middleware works well at scale — the new `requireStoreRole()`/`requireOwnStore()` middleware (`FLASH_STORE_ADMIN_DESIGN.md` §3.2) follows the identical shape, checking `req.storeRole`/`req.storeId` the same way `requireRole` checks `req.userRole`, but as a **third, independent** verification path (own secret, own middleware, own token), not a parameter bolted onto the existing one.

### 1.6 What's already well-positioned vs. what's a real bottleneck — a precise, honest scorecard

**Already well-positioned (confirmed, not assumed):**
- `admins.role` column — added specifically with future extensibility in mind (`ADMIN_PANEL_AUDIT_AND_VISION.md`, Addendum 3 §4), and `requireRole()` already generically supports any role string.
- `order_cancellation_store_shares` — already the correct `UUID` type, already documented as the explicit multi-store extension point, already being written to correctly (`orderController.js:416` writes `order.store_id || null` today).
- Driver app navigation — already reads the order's own `pickup_lat`/`pickup_lng`, not a hardcoded constant.
- `Order.create()` (the model layer) — already coordinate-agnostic; the single-store assumption lives at the controller layer, a clean, contained place to change it.
- The overall additive-migration discipline already used everywhere in `migrate.js` (`ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`) — the same idempotent, additive pattern this blueprint's own migration strategy (§3) recommends, already proven safe across 26 real migrations tonight alone.

**Real bottlenecks, honestly named:**
- `flash_inventory`'s single stock count per product — the one genuinely structural (not additive) change, per §1.2.
- `geoBoundary.js`'s single fixed bounding box + `FLASH_STORE_LOCATION` constant — must become per-store data, not a global constant, the moment a second city/region is involved.
- The `VARCHAR`/`UUID` store-id-shape inconsistency (§1.1) — small, but real, one-time cleanup needed before a `stores` table can be introduced cleanly.
- Zero tenant-isolation checks exist anywhere today, because there's never been a second tenant to isolate from — this isn't a bug yet, but §1.4's discipline needs to be applied deliberately and completely the day a second store's data exists, not retrofitted under pressure after a real leak.

## 2. Target architecture (concrete, not aspirational)

A real `stores` table (`id UUID PRIMARY KEY`, `name`, `address`, `lat`, `lng`, `service_area_bounds` — a per-store equivalent of today's single `NMB_BOUNDS`, `is_active`, `created_at`) becomes the single source of truth every current free-text/placeholder `store_id` column eventually points at via a real foreign key. `orderController.createOrder` looks up the real store row (by an authenticated, server-trusted `store_id` — from the checkout flow's own store-selection step, itself validated against `stores.is_active`) instead of the `FLASH_STORE_LOCATION` constant, and uses *that* store's real, registered lat/lng for the pickup point and delivery-fee distance calculation — `Order.create()` itself needs zero changes, since it already accepts arbitrary pickup coordinates.

Inventory becomes genuinely multi-location via a new `store_stock` table (`store_id`, `product_id`, `size`, `quantity` — the same relational shape as Saleor's real `Stock` join table, confirmed in `SALEOR_ARCHITECTURE_STUDY.md` §1.4), with `flash_inventory` itself becoming the shared product *catalog* (name, description, price, images — things that don't vary by store) while `store_stock` holds the per-location quantity. This is the one place this blueprint recommends directly borrowing Saleor's concrete relational shape, not just its spirit.

A new, separate `store_users` table and JWT domain (`STORE_JWT_SECRET`, its own login endpoint, its own `requireStoreRole()`/`requireOwnStore()` middleware) provides RBAC for the Store Admin Portal — every `store_users` row is non-nullably scoped to exactly one store by construction. This is fully additive and fully separate from the existing `admins`/`requireRole()` system, which is untouched. Full design: `FLASH_STORE_ADMIN_DESIGN.md` §3.

Everything else — orders, cancellations, payments, driver wallets, subscriptions, ratings — either inherits scope via an existing FK to `orders`/`users`/`drivers`, or (per §1.2's driver-pool/commission findings) deliberately stays platform-level, unscoped by store, because that's what's actually true about Flash's business model.

## 3. Migration strategy — incremental, additive, matching this engagement's own established pattern

This is not a big-bang rewrite; it's a sequence of small, independently shippable, `IF NOT EXISTS`-style additive steps, in the same spirit as every migration this engagement has already run against production tonight:

1. **Introduce the real `stores` table, with exactly one row.** Seed it with Flash's current single real store (its actual name, address, and `FLASH_STORE_LOCATION`'s real lat/lng). This alone changes nothing about current behavior — it's pure groundwork.
2. **Fix the type inconsistency (§1.1).** Convert `orders.store_id`/`store_boosts.store_id`/`store_promotions.store_id`/`brand_size_mappings.store_id` from `VARCHAR(100)` to `UUID REFERENCES stores(id)`, backfilling the single existing row's foreign key value (or `NULL` where genuinely never set, i.e. `orders`). Add the missing FK constraint to `order_cancellation_store_shares.store_id`. Zero behavior change — every existing row still resolves to the same one real store.
3. **Wire `orderController.createOrder` to read the real store row instead of the `FLASH_STORE_LOCATION` constant** — for exactly one store, this produces byte-identical behavior to today, and is the point where real, live verification (create a real order, confirm identical pickup coordinates/delivery fee to before) proves nothing broke before any second store ever exists.
4. **Build the checkout-time store-selection step** (even with only one real, active store to choose from) — this is where a customer's order gets a real, server-validated `store_id`, and it can ship and be tested completely before a second store is a live concern.
5. **Introduce `store_stock` alongside `flash_inventory`**, migrate the current single stock count into one row per size for the one real store, update `Order.create()`'s stock-check/decrement logic to read/write `store_stock` instead of `flash_inventory.stock_by_size` directly. This is the most involved step, correctly sequenced last among the "before a second store exists" steps, and worth its own dedicated verification pass given its structural size (§1.2).
6. **Only once all of the above is live and verified with one store: onboard a real second store.** This is the actual point where tenant-isolation risk (§1.4) becomes real for the first time — every store-scoped query needs its cross-tenant-rejection test run for real, with two real store accounts, before this step is considered done, not assumed safe.
7. **The new `store_users` table + `STORE_JWT_SECRET` auth domain + `requireStoreRole()`/`requireOwnStore()` middleware** (`FLASH_STORE_ADMIN_DESIGN.md` §3) — can be built and shipped any time after step 1, independent of the others, since it's pure additive, fully-separate auth-layer work with no dependency on the order/inventory changes and no interaction with the existing `admins` auth system.

Each step above is independently shippable and independently reversible (nothing is destructive; every step is additive or a clean type-widening), matching this project's own established migration discipline rather than introducing a new one.

## 4. Real risks

**Technical:** the `flash_inventory` → `store_stock` migration (§1.2, step 5 above) is the one piece of real data-migration risk in this whole plan — moving from "one stock count" to "one stock count per store" for real, live product data needs careful, verified backfill logic (every existing product's current count becomes that one store's count, not silently duplicated or zeroed). Query performance is the other real technical risk: once `orders`/`payments`/etc. are queried per-store at real multi-store volume, every admin dashboard query that currently does a full-table aggregate (`Admin.getFinancials()`, `Admin.getDailyTrends()`) needs a `store_id` index to avoid a sequential scan — see §6.

**Financial:** the pre-pickup cancellation split (10% store / 5% driver / 85% customer of item value, confirmed exactly via `orderController.js:62-69`'s real `computeCancellationSplit` function) is **today, correctly, Flash's own money**, since Flash is the only store — `ADMIN_PANEL_AUDIT_AND_VISION.md` §4.3 already flagged this precisely: "the moment a real third-party store exists, this same column becomes genuine pass-through revenue Flash *facilitates* but doesn't keep." This is a real, material change to Flash's own revenue recognition the day a second, independently-owned store exists (as opposed to a second *Flash-owned* location) — worth the founder's explicit attention as a business decision, not something this document decides. `driver_commission_debts` (§1.2) has the same shape: it's Flash's own logistics fee today by definition (there's only one store), and stays Flash's own fee even with multiple stores, *provided* Flash continues owning the delivery/logistics leg for every store — a real distinction to keep precise once a genuinely independent third-party store is being considered, versus Flash simply opening a second location of its own.

**Operational — resolved, no longer an open question:** the founder has explicitly confirmed Flash is being architected for genuinely independent merchants as the primary case, from day one, with no exceptions — not a coin-flip between that and Flash-owned locations. Every store gets independent ownership, authentication, employees, permissions, products, inventory, analytics, and settlements (`FINANCIAL_DOMAIN_SPECIFICATION.md` §3's real Store Settlement design is exactly this — a real bank transfer to a store's own account, not an internal accounting entry). A second Flash-owned location is simply the degenerate case of this same architecture — it still gets its own `store_id`, its own settlement record, its own everything, and the money happens to also belong to Flash; it is not a separate, simpler path that skips the machinery this document describes. The "merchant onboarding, merchant-facing payouts, merchant-level dispute handling" work once described here as deliberately out of scope for a Flash-owned-only future is now in scope by default — see `FINANCIAL_DOMAIN_SPECIFICATION.md` for the real, designed settlement/commission architecture.

## 5. Recommended order of implementation

Matches §3's migration sequence directly: (1) `stores` table + seed, (2) type-consistency fix, (3) `orderController` store lookup, (4) checkout store-selection, (5) `store_stock` inventory migration, (6) the new, separate `store_users`/`STORE_JWT_SECRET` auth domain — this one can run in parallel with 2-5, since it has no dependency on them and no interaction with the existing admin auth system — (7) onboard a real second store only once 1-6 are live and verified.

## 6. Security considerations — the single highest-stakes part of this document

Treated with the same severity rigor as every security audit this engagement has produced:

- **Every store-scoped query must filter by a server-derived `store_id`, never a client-suppliable one** — identical reasoning to `orderController.js`'s own existing pickup-coordinate trust boundary (§1.4), applied consistently to every future store-scoped endpoint, not just the ones obviously about orders.
- **The day a second store's admin account exists, every store-scoped admin query needs a real, live cross-tenant-access test** — attempt to read/modify Store B's data using Store A's real, valid credentials, confirm clean rejection — the same standard already applied to every user/driver ownership check this engagement has shipped (e.g. tonight's subscription-cancellation ownership tests). This is not optional hardening; it's the direct multi-store analog of an IDOR test, and should block shipping the second store the same way a missed ownership check would block shipping any other feature.
- **Corrected: the existing `admin_actions` audit log stays exactly as it is** — it only ever logs internal Flash-team actions and needs no store-scoping, since internal admins aren't store-scoped. The Store Admin Portal needs its **own**, separate `store_actions` audit log (`store_user_id`, `store_id`, `target_table`, `target_id`, `metadata`) — a structurally distinct table, not a column added to `admin_actions` — so a future dispute ("did this Store Manager touch another store's order") is answerable from a log that itself proves the store scope at the time of the action. Full design: `FLASH_STORE_ADMIN_DESIGN.md` §5.4.
- **A driver's or customer's JWT should not gain a `store_id` claim** (per §1.5) — adding tenant scoping to roles that are deliberately *not* tenant-scoped in Flash's real business model would be a real, unforced security-surface increase (one more claim to validate, one more way to get the scoping wrong) for a scope that doesn't correspond to anything real for those roles.
- **The existing `payment_methods`/`transfer_recipients` exclusion reasoning stays correct and unaffected** — these are already correctly excluded from admin visibility entirely (`adminCoverage.js`'s `intentionallyExcluded` list) for PCI-scope reasons unrelated to store-scoping; multi-tenancy doesn't change that reasoning or reopen it.

## 7. Performance considerations at real scale (thousands of stores)

- **Index every new `store_id` column used in a `WHERE` clause** — `orders(store_id)`, `flash_inventory` via `store_stock(store_id, product_id)` (a composite index, since that's the real lookup shape), matching the same chronological-indexing discipline already established for the admin panel (`RESOURCE_TIMESTAMP_COLUMNS`, `adminResourceDefaults.js`, enforced by `adminChronologicalSort.test.js`) — a `store_id` index needs the same kind of enforced discipline, not an afterthought added when a slow query is first noticed in production.
- **`Admin.getFinancials()`/`Admin.getDailyTrends()`'s aggregate queries** (`Admin.js`) need a `store_id` filter *and* a covering index once real multi-store volume exists — today these run full-table aggregates because there's only ever been one store's worth of data; at "thousands of stores" scale, an unindexed per-store filter on these queries would mean a sequential scan on every dashboard load, the exact kind of query-pattern regression this engagement's own earlier load-testing/chronological-ordering work (referenced in `adminCoverage.js`'s own comments about `RESOURCE_TIMESTAMP_COLUMNS`) was built to catch and prevent.
- **`autoMatchService.js`'s nearest-driver query** (`autoMatchService.js:36-56`) — confirmed to have **no store filtering today, by design** (§1.3) — stays a citywide/regional proximity query, not a per-store one, so its performance profile is genuinely unaffected by store *count* the way an isolated-per-tenant query would be; its real scaling concern (driver density in a given geography) is unrelated to multi-tenancy and out of this document's scope.
- **`geoBoundary.js`'s single bounding-box check** (`isWithinNelsonMandelaBay`) is an in-memory numeric comparison, not a query — replacing it with a per-store lookup (§1.3) adds one indexed `stores` row-read per request, a negligible cost at any realistic scale, not a performance risk worth over-engineering against.
